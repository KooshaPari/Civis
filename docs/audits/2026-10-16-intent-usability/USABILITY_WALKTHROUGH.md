# Player journey and acceptance witnesses

Expected qualification journey, not a playthrough performed by this docs lane. Use allowed process/file/log/CLI receipts plus direct operator attestation for presentation/interaction; never screenshots, recordings, screen/pane captures or capture-enabled harness steps. Headless evidence cannot automatically satisfy visual/audio acceptance.

```text
Install -> load settlement -> understand constraint -> god intervention
 -> leader direction -> inhabit person -> save/quit/reopen
 -> continue -> unattended evolution -> inspect real consequences
```

| Checkpoint | Required user outcome | Independent witness / failure case |
|---|---|---|
| Install outside checkout | Correct selected client/assets and matching server/profile start | Artifact/source/config hashes and process logs; missing required asset fails explicitly |
| Enter living world | Water/food constraint can be identified, with affected population | Scenario/checkpoint identity and independently adjudicated world values; no empty scene presented as the game |
| Act as god | Intervention has bounded meaningful effect | Before/after source-backed state and player task record; failed action must not return success |
| Redirect leader | Orders alter behavior consistently with authority and resources | Stable leader identity, accepted order and observed consequence; stale/unauthorized command rejected |
| Inhabit person | Continue as same affected individual with understandable controls | Stable entity/intent and world continuity; role switch cannot duplicate resources or lose identity |
| Save, quit and reopen | Resume evolved world rather than rebuild original seed | Semantic save manifest covers physical/social/cultural/faction/AI/mod state; IDs/relations reconcile; corrupt/missing fields fail closed |
| Resume after change | Supported save migration preserves meaning | Prior-version fixture and recovery witness; backups available, unsupported version explicit |
| Leave background run | Progresses within approved resource/time budget | Process uptime/resource log, checkpoint hashes and actual event/state deltas; no invented unattended summary |
| Judge playability | Roles, presentation/audio and causal loop are convincing | Direct independent operator task feedback; no screenshot ban interpreted as automatic visual pass |

Existing game E2E and playthrough failures must first be classified as harness/build framing versus product failures. PR1598/1593 already own server-binary/framing repairs; reuse their results. A server missing before gameplay cannot support a gameplay-complete claim, but also does not by itself prove simulation behavior is broken.

Adversarial cases: populated faction relations, cultural/social state loss, stale actor IDs after role switch, interrupted save, incompatible mod state, LOD duplication, background time jump, missing assets, unreachable server, corrupt response framing, unsupported native profile and false summary claims. Keep expected outcome oracles independent from the implementation.
